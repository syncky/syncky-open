# Syncky minimal agent

The smallest complete agent for the Syncky relay, written to be read and copied: one file, [`agent.mjs`](agent.mjs) (at most 450 lines, Node ≥ 22.15, four pinned dependencies: `@hpke/core`, `@hpke/dhkem-x25519`, `@hpke/chacha20poly1305`, `qrcode-terminal`). It registers (with an invite only when the relay requires one), shows the pairing QR and code, confirms the phone by the proof it sends after the owner picks that code, polls and opens end-to-end encrypted `sync` messages, acks them, and sends one `dietary_water` HealthKit write whose app ack it then sees. No webhook server, no database, no web UI: state is one JSON file. It is a teaching example: it prints sample type counts, keeps no samples, and is not hardened for an unattended server; whoever runs it is responsible for the data it decrypts.

The integration guide [agent/AGENTS.md](../../agent/AGENTS.md) describes the thin transport boundary and links to this independent walkthrough. Error codes, limits and troubleshooting: [agent/docs/REFERENCE.md](../../agent/docs/REFERENCE.md). The operational thin agent with generic send/inbox/receive and a 30-day raw history is in [agent/](../../agent/README.md).

## Commands

```bash
npm ci
export SYNCKY_HOME="$HOME/.syncky-minimal"   # default ./.syncky-minimal; state.json is mode 600 in a 700 directory
./agent.mjs init --relay <url> [--invite <invite>] [--name <name>] # keys + register (E1); the invite may come from $SYNCKY_INVITE instead
./agent.mjs pair [--wait <seconds>]                                # QR + code, wait until the phone joins and proves the code
./agent.mjs poll [--once]                                          # fetch, open, summarize, ack; every 30 min, every 5 min after send-water
./agent.mjs send-water <liters> --to <member_id>                   # one sealed write command (E10)
./agent.mjs status                                                 # members, last seq, commands and their acks
```

`pair` prints a version 2 link (with a fresh 16-byte pairing secret `c`), its QR code and the pairing code (`code: 482 913 057`); send the owner the link and the code together. After joining, the phone asks the owner to pick the last group of the code and, for the right pick, sends a `pair_proof` control envelope. `pair` stores the proof it expects for the key the phone joined with (an HMAC keyed by `c`; `c` itself is never saved), keeps reading the inbox like `poll --once` until the proof arrives, then confirms the phone and sends it a `confirmed` control envelope. A proof that does not match revokes the phone (E9) and `pair` exits 1; so does a phone that leaves meanwhile (a wrong pick cancels the pairing on the phone). If `--wait` (default 600 s) ends before the proof, `pair` exits 1 and a later `poll` still confirms the phone. A phone that joined after its `pair` ended has no stored proof and can never be confirmed: the next `pair` revokes it first, or as soon as its messages turn up while `pair` waits for the new phone's proof. If E9 or sending `confirmed` fails, the phone stays joined and the proof stays unacked, so the next `poll` checks it again. `confirmed` is the only control envelope the agent sends. Data envelopes from a joined but unconfirmed phone are neither opened nor acked, nor is its `pair_proof` while no proof is stored for it: `poll` stops there. Marked access `control` envelopes are authenticated and decrypted, checked for `v=1` and the `access_request`/`access_reply` type matching the marker, then skipped. Other controls (system messages such as an unpair reason) are acked without being opened. Both skips print `seq N: skipped (control message)`; the version 2 app sends nothing but its `pair_proof` before it is confirmed. Output shows type counts and codes only, never sample values, tokens or keys; a corrupted `state.json` exits 1 with a fixed message that does not quote the file. The minimal agent ignores the `scope` a phone sends in every `sync` message (what it shares and what the agent may write) and shows a write the owner left out of that scope as `rejected` with the reason `type_not_in_scope`.

The operational `pair` command always emits `syncky://` for Syncky (production), regardless of the relay hostname; it has no environment inference or URL-scheme override. Use the [thin agent](../../agent/README.md) for Syncky Dev (`syncky-dev://`) or Syncky β (`syncky-staging://`), with `syncky-agent pair --url-scheme syncky-dev` for local Debug pairing. The minimal parser accepts all three schemes and the low-level builder accepts an optional `url_scheme` for shared vector replay, defaulting to `syncky`; this does not configure its CLI.

The example is already at its 450-line cap, so it does not implement automatic first-sync fast polling. For that behavior use the [thin agent](../../agent/README.md) with `receive`. When extending this example, use one poll loop: after confirmation, poll every 30 s until the newly confirmed phone's first complete `sync` (`more: false`), or 60 s before the earlier of its relay `joined_at` + 15 minutes and pairing `completed_at` + 15 minutes, then resume the normal interval. Persist the relay anchor and completion per phone; local join-observation time must not extend the window. Keep advertising the configured interval and let Retry-After win over the shorter delay. The current example's printed type counts do not expose `more`, so they cannot tell an external poll wrapper that the first sync is complete.

Exit codes: 0 ok, 1 relay or protocol error, 2 bad arguments, 3 not initialized. A `state.json` that group or others can read is refused with exit 1 on every command; `chmod 600` it. `poll` can keep running in another terminal while you run `pair` or `send-water`: each change re-reads `state.json` while holding the lock file `state.lock` next to it, which names its owner's pid. A lock whose owner is no longer running is taken over; a running owner is waited for, however long. If a command exits 1 saying `state.lock.claim` was left by a process that is no longer running, remove that file and retry. Run only one `poll` at a time. `send-water` does not resend: if it exits 1 the command stays `pending` and the relay may still have accepted it, so run `poll` and `status` (and check the phone) before sending again, because a second `send-water` is a new command that the phone applies too. During Launch the hub is active and free, so `send-water` is not refused for the plan; after Launch grace `send-water` exits 1 with `relay 402 hub_suspended` and `poll` prints `hub_suspended`. On a hub without the owner's Sync + Relay plan the relay refuses every data envelope: `send-water` exits 1 with `relay 402 hub_unpaid` (or `hub_suspended` once the plan expired) and the command stays `pending`; send again after the owner renews. If every call fails with `invalid_token`, the token was revoked or the hub was deleted: no plan within 7 days of the latest phone join/leave, or 7 days after the plan finally ended (Apple grace stays active; reported billing retry suspends without a countdown until final expiry or the 60-day cap from the period end). This minimal agent prints the events and the hint without tracking hub state: remove `state.json`, then `init` and `pair` again.

Send budget: the relay allows each agent one new `data` envelope per 5 minutes with a burst of 3 and answers `429 rate_limited` with `Retry-After` past it (`control` envelopes and phones are not limited). `send-water` posts one command per call, so run it at most once every 5 minutes; after a longer `Retry-After` it fails with `rate_limited` and the wait, and the command stays pending. A caller using the thin agent supplies its own complete `commands` JSON, batching explicitly approved writes deliberately and respecting the relay budget and Retry-After. The transport does not batch or assign command ids/versions.

## Tests

From this directory:

- `npm test`: the shared vectors in `protocol/test-vectors/` (envelopes of both kinds, pairing URIs v1 and v2, pairing codes and proofs; `test/vectors.test.js`), the CLI (`test/cli.test.js`), every relay call against a stub relay (`test/relay.test.js`: the proof check, `confirmed`, the revoke on a wrong proof, `pair` beside `poll`), and the size and import guard (`test/size.test.js`). Marker vectors cover all three values and AAD tampering; relay fixtures cover a marked diagnostics report followed by cursor/ACK persistence, reopen and the next sync, as well as wrong-inner rejection and unmarked compatibility.
- `node --test test/e2e/minimal-agent.e2e.test.js` with `SYNCKY_E2E_RELAY` set to a relay that registers agents without an invite: the CLI with the scripted phone from `agent/test/support/fake-phone.js`: pairing by the phone's proof without a prompt (the phone receives `confirmed`), a day of steps and heart rate, a water command and its `applied` ack, and a proof for another device key that revokes the phone.

Marked and legacy unmarked diagnostics reports are authenticated and decrypted as data, then skipped with a fixed generic label. `agent.mjs` validates the optional `diagnostics` marker/kind matrix and, for opened data, requires an `archive` marker to match `type=diagnostics` before the generic skip. Both crypto layers use base AAD followed by `|control` when applicable and then `|diagnostics=<value>` when present, in that fixed order. A missing marker keeps the old bytes; added/stripped/changed markers and marked legacy-AAD ciphertext fail without fallback. Ordinary sends omit the marker. The relay sees the claimed purpose but cannot verify the encrypted contents. Polling persists the cursor and sends the transport ACK, including across restart; subsequent sync messages are processed normally. This walkthrough does not store, read or request diagnostics reports. Use the thin agent's `inbox --type diagnostics` to read durable raw reports, and `send --type diagnostics_request --json <file|->` for explicitly approved requests described in its [verified skill](../../agent/skills/syncky/SKILL.md#diagnostics-request). A transport ACK alone does not establish diagnostics report storage.

The phone's Check/View/Download work in every plan without this example. Local Check sends nothing; explicit summary refresh/diagnostics report preparation can read member-authenticated evidence, while only manual Send or Review → Confirm sends a diagnostics report E2E. This example has no Confirm/request/outcome implementation; use the [thin agent skill](../../agent/skills/syncky/SKILL.md#diagnostics-request) for generic CLI/MCP requests and raw diagnostics/diagnostics_reply outcomes. `diagnostics` uses data; `diagnostics_request`/`diagnostics_reply` use encrypted controls, with schemas/vectors in the [protocol guide](../../protocol/README.md#diagnostics-data-and-consent-controls). Unknown controls are skipped; a request to an older client eventually expires. Missing summary routes are explicit and diagnostics reports still obey ordinary 402 data gates.

The diagnostics report has one 180000-byte inner cap within a 262144-byte envelope. Phone history/manual retries expire after 48 hours; thin-agent raw inbox history lasts 30 days from receipt; request-bound diagnostics reports stop at 24-hour expiry, replies retry for 48 hours from the decision, and downloaded copies remain user-controlled. The phone keeps one pending request, a 24-hour request expiry and one diagnostics report per rolling 24 hours per agent pairing. The thin agent has no local request admission or cooldown policy. Marked relay traffic has independent per-hub UTC-day admissions (30) and outstanding queue caps (2 MiB/100 rows), plus separate token RPM. Diagnostics 429 reasons are `diagnostics_quota` (until UTC midnight) and `diagnostics_queue_full` (300 seconds); ordinary queue caps retain `queue_full`. Legacy unmarked traffic retains ordinary accounting. Deploy relay support before new senders and update both endpoints; old Dev/pre-marker receivers must update without stripping markers. The thin agent retries sealed diagnostics traffic independently of ordinary sends. A generic request push and an exact local or remote tap open the matching available Review; arrival prepares nothing and only Confirm sends. Wake/contact evidence is bounded and APNs acceptance is not delivery. Diagnostics use hashed references, not raw lookup ids, and are neither identity proof nor a complete access export; verified requests use the app's Privacy requests flow.

## Unsupported Health access requests

The thin agent offers generic send/inbox for `access_request` / `access_reply`; this example has no access command, decision UI, cooldown storage or scope mutation. It validates `access=request|reply` on control envelopes, mutually exclusive with `diagnostics`, and checks the authenticated inner type before safely skipping it with no reason/type/body output. Unmarked access inners, dual/malformed markers and kind/type mismatches are rejected safely. Both HPKE Auth and payload AEAD bind base AAD followed by optional `|control`, `|diagnostics=<value>` or `|access=<value>` in fixed order, without legacy fallback. The phone requires both request and largest reply to fit 4096 serialized control-envelope bytes; the thin transport bounds each envelope and callers respect the phone's request limits. Unsupported/poison controls do not block cursor advancement, ACK or later ordinary sync processing. The minimal agent's durable cursor survives reopen; the browser demo remains memory-only and reload starts a new session. Use the [thin agent access skill](../../agent/skills/syncky/SKILL.md#access-request) for explicit consent, outcomes and next-sync scope; update old endpoints rather than stripping markers.
