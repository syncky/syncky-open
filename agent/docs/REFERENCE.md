# Agent reference

The CLI surface is init, pair, wait, confirm, reject, revoke, forget, status, send, inbox, receive, ack, skill, mcp, selftest and help. The `syncky` alias is identical. All data responses are JSON except private pair QR/code and plain skill/diff. Global flags: --home, --relay, --url-scheme, --log-level, --help. For send only, --json selects a file or stdin (-); it is never an output flag. See [README](../README.md) and [SETUP](../SETUP.md).

Pairing defaults to HTTPS links. Explicit `--url-scheme`, `SYNCKY_URL_SCHEME` or saved `url_scheme` selects legacy output for scanning inside Syncky or pasting with preview and consent only. Tapping a legacy pairing link or using the system Camera does not start pairing. After installation, reopen the HTTPS link, copy it and paste it in Syncky, or scan the agent’s QR code inside Syncky.

## Limits and transport

Hosted defaults: a pairing link lasts 10 minutes; the relay response's `expires_at` is authoritative. A never-joined hub lasts 24 hours from registration; creating another link does not restart that clock. Every human `pair` output labels both defaults and prints the relay deadline. JSON adds value-free `limits` metadata: `hosted_defaults` contains `pairing_link_ttl_s: 600` and `unjoined_hub_ttl_s: 86400`, `pairing_link_deadline: "expires_at"` identifies the authoritative field, and `unjoined_hub_clock: "registration"` identifies the clock origin. These defaults are guidance, not a newly calculated hub deadline.

One receiver lease per home; receive --once performs one bounded cycle. Receive prints no records to stdout by default; records remain durable and available through inbox and MCP. `receive --emit-records` writes private JSONL to stdout, including with `--once`. Poll interval defaults to 1800 seconds, configurable 300–86400. Preserve Retry-After, daily heartbeat and first-sync fast polling. A missed expected poll can show Needs attention on the phone. MCP starts no receiver/heartbeat/background retry loop. Read-only calls fetch no updates and mutate no Health data.

Envelope maximum: 256 KiB (262144 serialized UTF-8 bytes, including base64 ciphertext and recipient metadata); controls 4096; diagnostics inner 180000. The CLI separately caps raw JSON input at 262144 bytes; input below that cap can still exceed the sealed envelope limit. The signed skill-update JSON envelope has an independent 262144-byte cap and a 131072-byte decoded payload cap. Seven recipients maximum. Marker and both AAD operations follow the bundled/verified table. Unknown types use unmarked control; authenticated incoming JSON is preserved without feature-schema validation. --validate checks available local schemas without fetching refs. Phone policy/consent remains authoritative.

`end` must not be later than now + 1 h; the phone rejects a later `end` with `invalid`. For a running daily total, set `start` to local day start and `end` to now or the last diary entry time. Never use the end of the day. When a total changes, resend the same `command_id` with `version` + 1.

The phone accepts command trees with at most 32 nested object/array containers, including the command object, counting unknown fields before normalization. A deeper command is dropped as an invalid field while ordinary siblings remain usable; shallow unknown fields are retained. This also bounds commands in direct-server replies and single-command evaluation. The complete JSON document limit remains 128 containers.

Access-request timestamps must have an original positive interval of at most 24 hours and must still have a positive interval of at most 24 hours after normalization to persisted millisecond precision. An interval collapsing to zero is invalid with `detail: ttl`. General RFC 3339 parsing still accepts nanoseconds.

Phone and direct-server saves validate the complete serialized candidate before replacing last-good durable bytes. A failed validation returns local `storage` with fixed reason `state_candidate_invalid`; the run's cursor is not committed and the same envelope can be fetched again later. This prevents corrupt replacement, without repairing already-corrupt state or automatically recovering from an unhandled poison item.

Put all nutrients of one day in one `send` with several `commands`. Send several entries in ONE `send` with a `commands` array; the transport does not combine separate calls. The 256 KiB (262144 bytes) data-envelope cap counts the complete serialized UTF-8 JSON, including base64 ciphertext and recipient metadata. The inner `commands` JSON can be up to roughly 191 KiB for one recipient, less with more recipients. The relay allows a burst of up to 60 data envelopes per agent, then about one a minute (about 60 data envelopes per hour per agent sustained), within the per-token limit of 60 requests a minute shared with polling, ACKs and heartbeats. A 429 `rate_limited` from either limit is retried automatically by the outbox after `Retry-After` when the receiver runs, so the caller does not resend. `status --json` shows `transport.send_lanes` (lane id to next allowed Unix time in milliseconds, including any legacy data-lane deadline) and pending `sends` with `code`, `next_attempt_at` and `retry_after_until`.

Inbox pagination: limit 1–1000 (default 100), member/type/after-seq/since/until filters, at most 1 MiB per page. Continue from next_after_seq while has_more. Explicit ACK cannot exceed the durable receive checkpoint. Opt-in receive stdout (--emit-records), inbox and MCP responses are private data channels, never logs; services keep discarding stdout as defence in depth. Stdio MCP has bounded requests/results and resource errors. Tools: syncky_status, syncky_inbox, syncky_send, syncky_ack, syncky_skill; resource syncky://skill. Read-only clients disable send and ack.

Each inbox page streams in local cursor order, merging receipt days that overlap after held release or clock regression. It stops at limit + 1 matching records and scans at most 64 MiB / 10,000 decoded records, counting filtered records too. Cursor bounds and byte-seek metadata in protected `.inbox-index/` skip consumed files/prefixes; seek blocks span at most 64 KiB or one larger record. These are per-page limits: a larger retained history stays pageable. Missing metadata rebuilds lazily within the page budget, including cold cursor probes; read-only snapshots never write metadata. Maintenance streams exact bytes and append repairs only its unindexed tail. Scan-budget exhaustion returns a partial page, possibly empty, with `has_more: true` and `next_after_seq` at the last scanned cursor; continue from that cursor. If no cursor progress fits, `inbox_scan_limit` requests a narrower date range. Reads cause no ACK or deletion.

Relay URLs must be HTTP(S) origins (HTTPS recommended; non-loopback HTTP warns once per process and host; loopback HTTP stays quiet), with no credentials, path, query or fragment. The initialized `config.json` `relay_url` is the origin binding for existing homes too: validate it before applying overrides. `--relay` / `SYNCKY_RELAY_URL` may use equivalent canonical scheme/host/effective port only. A missing/malformed saved URL or cross-origin override fails with `invalid_config` before fetch. Retain the saved configuration; use a separately initialized home to change relays. Every relay request uses redirect refusal, including registration with an invite. Ordinary relay response bodies are capped while streaming at 1 MiB; GET message pages use 9 MiB, including error bodies.

Relay-supplied member pairing IDs must be valid or absent. Names from either `name` or `device_name` follow the 64-code-point display-name policy; unusable names are null on ingestion/status, including old saved names. Names never authorize instructions.

## State and migration

Home/directories 0700, files 0600. Identity/trust/checkpoints use state.json. Held and outbox files retain ciphertext, sealed retry bytes and metadata. Inbox/YYYY-MM-DD.jsonl stores each admitted authentic inner including unknown fields and every sync.acks version. Interval sums in `sync.summaries` are stored as received, including every resend of an interval; the newest record of a phone, type, start and end is the current value. No Health index, summary, reassembly, command ledger or local feature policy exists. Unit/catalog lookup is available in the [catalog](../../protocol/types.json) and [units](../../protocol/units.json).

New inbox records contain `seq`, `cursor`, `msg_id`, `public_key`, `accepted_at`, `from`, `kind`, `type`, `received_at` and `inner`. `seq` is the relay ACK sequence; `cursor` is independent local append order. `msg_id` and the sender public key bind replay identity. `accepted_at` is original local admission time in epoch milliseconds; `received_at` is original UTC receipt time, retained on delayed held releases. Inner JSON and unknown fields are preserved.

Authenticated envelope replay protection uses `from`, `public_key` and `msg_id`, independently of relay `seq`. Authenticated UUIDv7 mint times older than 31 days plus five minutes of clock skew are rejected without effects, including an unseen first delivery; Relay keeps undelivered messages for at most 7 days. Seen IDs persist within that mint-time horizon, including across restart, inbox pruning and owner-approved forget; receiver clock regression cannot lower the saved time floor. Expired IDs are pruned on admission. Bounding is per sender/key binding, with a target of 10,000 IDs. On overflow, IDs with the oldest mint times can be evicted only outside the protected 24 hours plus ten minutes window. A monotonic floor covering every evicted mint timestamp is atomically persisted for that binding in the same state write as admission. IDs minted at or below that floor, including unseen IDs and timestamp ties, are rejected as expired without a record, emission or effects, while permitting durable relay ACK progress. An unseen ID inside the protected window remains eligible even above the target; another sender's floor cannot reject it. At 90,000 retained IDs per binding, exceeding the protected window's allowance at 60 requests/minute, `inbox_seen_limit` stalls new admission before append and leaves the page unACKed. Other senders in that page can still be admitted; retry after older IDs leave the protected window. A retained duplicate adds no record or emission and repeats no scope, pairing, reply, wait or release effects, while permitting durable relay ACK progress. Append/fsync or state admission failure leaves new ciphertext unACKed. Interrupted durable rows recover their effects before later inbound effects; reads exclude an uncommitted row. Older UUIDs remain rejected beyond this age window. Existing 0.1.4 rows without IDs remain readable, but their missing identities cannot be reconstructed, so a resequenced replay of such an old row cannot be recognized until its authenticated ID has been observed.

Same-home owner-assisted offline migration preserves secrets/config/pairing and trust; a legacy home without exported state returns migration_required. Init refuses initialized homes. Legacy agent.db/diagnostics.db/access.db and WAL/SHM are never opened or deleted by this runtime. Status names them for manual owner handling. Unpair/Delete Relay data/token revocation retain history under its original sender; 30-day receive-time pruning affects thin inbox files only, at loop startup and daily. Each outbox flush retains the latest 100 sent/failed receipts by message id; pending sends remain until delivery or terminal failure. Explicit owner-approved forget after revocation removes the member's thin inbox/held/outbox data, retaining its revoked tombstone and all legacy files.

If the phone says the relay was not told, explicit owner-approved `revoke <member_id>` revokes a known phone on the relay before revoking locally; history stays until `forget`. JSON returns member, state and revoked_on_relay: true for relay success, false for 404; other relay errors leave local state unchanged, and repeated revocation succeeds.

### Recover when `invalid_token` arrives before any phone joined

`invalid_token` means the relay refused this identity; it does not prove why. A never-joined hub may have expired, the hub may have been deleted, or the token may have been revoked or otherwise refused. The hosted default is 24 hours from registration for a hub no phone has ever joined. Creating another pairing link does not restart that clock.

1. Stop and tell the owner. Obtain explicit owner intent to create a new identity before registering again; do not retry registration automatically.
2. Stop the old receiver by its known service identity or known PID. Stop its supervisor too so it cannot restart it. Use the recorded unit, launchd label or scheduled task, or send SIGTERM to the known receiver PID; never stop processes by a broad name match.
3. Retain the old private home and its history. Choose a fresh, unused absolute `--home` path on the **same relay** saved for the old home. Replace the placeholders below; the CLI creates private directories/files. Do not overwrite the old home, edit its credentials, transfer tokens or change environments to get past the refusal.

```sh
syncky --home '<fresh-absolute-home>' --relay '<same-relay-url>' init --name 'My agent'
syncky --home '<fresh-absolute-home>' --relay '<same-relay-url>' pair --no-qr
```

4. Show the new private link/code only to the owner and complete pairing again. If the phone reports `pairing_not_found`, ask for a fresh setup/link; that error alone does not prove deletion either.
5. Repoint the chosen receiver and MCP together: replace their `--home` arguments and/or `SYNCKY_AGENT_HOME` environment settings with the fresh path, removing stale overrides. Pin `--relay '<same-relay-url>'` in both configurations so an inherited `SYNCKY_RELAY_URL` cannot select another relay. For the receiver use `syncky --home '<fresh-absolute-home>' --relay '<same-relay-url>' receive`, retaining its approved flags/schedule; for MCP use `syncky --home '<fresh-absolute-home>' --relay '<same-relay-url>' mcp`. Start only the receiving mode already approved by the owner, using the same fresh home; a new service or schedule still needs explicit approval.

The new identity does not inherit old trust or history. Old history remains under its original senders in the old home and is accessible offline with `syncky --home '<old-absolute-home>' inbox --limit 100`; keep that home private. Recovery does not delete it or move it into the new identity.

## Requested access at pairing

From agent 0.1.4, with explicit owner approval for the exact types, use `syncky pair --read body_mass,heart_rate --write dietary_water`. Either flag is optional; an omitted side is empty. Names are sorted and deduplicated, must be catalog types, and writes must be writable. At least one type is required when flags are supplied. Both the request and worst-case reply must fit the 4096-byte encrypted control envelope cap; there is no separate type-count or URL-length cap. The generated `request_ref` is fresh 32-lowercase-hex randomness. The optional `request_ref`, `read` and `write` fields follow existing parameters in the private fragment; neither scope nor credentials enter the browser's HTTP request to the pairing page. The link contains credentials and the requested Health type names; anyone who sees its full text can read them. With no flags, legacy no-scope pairing is unchanged, including v1 fingerprint confirmation. Requested scope works with both v1 and v2.

The phone reviews Read and Write items, with per-type choices, Allow all and Decline all. Allow all submits your choices and continues pairing; iOS asks only about listed types it has not decided yet. Decline all opens no Health sheet and grants empty scope. Choices made at pairing have no quota; a type declined at pairing starts the same seven-day wait. Pairing grants stay with this agent and do not change the app-wide Health selection or write allowance. You can change or stop this later under Connections › this agent › Data types, or unpair it. After confirmation, the standard `access_reply` reports `allowed`, `declined` or `needs_health_settings` for each requested item. `status --json` retains requested types and outcomes after `pairing.json` is removed. CLI and MCP status omit request refs; response waits expose only kind, member, state and timing metadata. Outcomes describe the decision; only authenticated `sync.scope` updates effective scope. The phone sends this scope promptly without sample collection or a manual initial Sync. Read authorization remains unobservable; follow Health Settings guidance for `needs_health_settings`.

A confirmed pairing without a matching reply does not establish consent or a decline. Status keeps `awaiting`, then `no_reply` after the 15-minute post-confirmation deadline; a late matching reply can still resolve it. Check the phone, connectivity and pending consent. Only with renewed explicit owner intent and phone availability, use `send --type access_request --validate --json <file|->` with the same intended types, a fresh `request_ref`, and current timestamps with finite positive TTL up to 24 hours (`0 < expires_at - created_at <= 24h`). No automatic fallback is sent. Never invent outcomes or scope. See [the access request example](../skills/syncky/SKILL.md#access-request) for complete JSON.

Later explicit `wait` uses the link in `pairing.json`: a completed binding for that same pairing remains available after link or reply expiry, while an expired or pending-past-grace link returns `pairing_expired`. Only when no pairing file remains does it return the latest eligible completed binding to the current phone and key. Confirmed trust stays confirmed; a joined phone returns its fingerprint and still requires owner confirmation. Revoked, rejected, forgotten or unpaired bindings are excluded. These local results need no expired-link lookup; the detached waiter remains bounded.

A running receiver uses a separate 300-second response polling schedule after scoped pairing and successfully sent access requests, diagnostics requests or commands awaiting acknowledgments. Matching replies/acks or expiry close only their own waits. Pairing waits use link expiry before join, 15 minutes after verified join for confirmation, then 15 minutes after confirmation for the reply; command ack waits last 15 minutes from first successful send, and request waits end at request expiry. These bounded waits are separate from the existing 25-second first-sync join window and the configured background cadence (default 1800 seconds). `receive --once` ignores configured cadence once the 300-second floor has passed, while preserving existing join/pagination exceptions and Retry-After. A deferred result includes `reason: "poll_floor"` or `reason: "retry_after"` and `next_poll_at` in epoch milliseconds. MCP starts no receiver and has no pairing tool; later requests use generic `syncky_send`.

## Requests and results

Use generic send with complete caller-owned JSON; see [skill](../skills/syncky/SKILL.md). Explicit writes need owner intent for exact value/time or an approved standing rule. Sent/relay ACK is not applied. Keep stable command_id/version and correlate every per-version reply, including applied/rejected/deleted_by_user; no local dedup by command id exists.

`access_request` is an optional ask-ahead, not a required step before writes. For a catalog-writable type without an explicit decline, a phone ack of `type_not_in_scope`, `type_not_allowed` or `healthkit_denied` means: tell the owner to allow that type on the phone (including Health Settings for iOS denial). With explicit owner approval, send an `access_request` for exactly those write types if the phone has not asked yet. Resend only after the next ordinary sync shows the effective write scope. A refused write creates no access request or automatic system consent prompt; its Home card may offer an owner-tapped Allow action. Unknown or read-only types cannot be enabled; correct the type instead.

On `declined_by_user`, stop automatic writes and access requests for that type. A later `access_request` requires renewed explicit owner intent and phone availability after its seven-day decline wait and other per-type waits (`next_available_at` when supplied). Retry a write only after the next authenticated sync shows that type in the effective write scope and the owner has approved the write.

On an `invalid` ack, check the command format first (`--validate`): fix timestamps, units or JSON. Schema validation does not cover phone policy; check interval bounds and units, then report an unexplained rejection without looping. Never ask for access on `invalid`. After a phone rejection, keep the same `command_id` and increment `version` before retrying; the phone caches completed rejections.

CLI `send` and MCP `syncky_send` durably queue ciphertext and attempt delivery. A successful call can return `state: "pending"` when another sender holds the delivery lease or a retry is due; the separately running receiver continues delivery. Poll `status --json` or `syncky_status`, matching `sends[].msg_id` to the receipt, until `state: "sent"` (relay acceptance) or `"failed"`. Use a bounded deadline that allows Retry-After; do not resend merely because the receipt is pending. Phone application still requires its matching inbox reply.

Diagnostics and access also require explicit owner approval. Diagnostics require Review and Confirm on the phone. The phone limits pending requests and admission; diagnostics requests expire after 24 hours and access requests use finite positive TTL up to 24 hours. From phone 0.1.3, access allows at most five admitted requests per agent per rolling 24 hours (amendments count), at most three amendments per pending request, a 24-hour per-type wait with read and write counted separately, and a seven-day wait after an owner decline across both read and write. Choices made at pairing have no quota; a type declined at pairing starts the same seven-day wait. Read actual diagnostics/diagnostics_reply/access_reply through inbox, then next ordinary sync's scope. `access_request` lists are sorted and deduplicated before sealing. `--validate` / `syncky_send` validation checks known types and writable writes before anything is sent: a `write` list naming a type the catalog marks `write: false` (for example `walking_speed`, which Apple computes) fails locally with `schema_invalid`, `detail` `not_writable` and the offending `types`, while the same type under `read` passes; use finite positive TTL up to 24 h (`0 < expires_at - created_at <= 24h`); 24-hour examples are defaults. An `access_reply` with outcome `invalid` carries an optional value-free `detail` (`unknown_type`, `not_writable`, `ttl`, `empty`, `reason_too_long`, `malformed`, `created_in_future`, `too_large`); read it in the raw inbox, correct the request and use a new `request_ref`. It grants no access.

For post-pairing access requests, Allow adds only approved types to Health selection, without selecting their categories. Existing selected categories and individually allowed types are preserved. **Choose Health data** shows partial selection as **Individually allowed: …** under an unchecked category; Allow texts name the exact types. Existing read `all` stays `all` and follows later Health selection changes. Approved reads turn `none` into a chosen list and are unioned into existing read lists. Unchecking a category leaves individually allowed types selected. To stop those too, use **Remove individually allowed types** below the category and save; iOS permissions stay unchanged.

Relay allows one visible access alert per sender per hub every five minutes and at most five visible alerts per rolling 24 hours. One admission covers all eligible device tokens; no token means no admission, identical envelope retries spend nothing, and APNs failure gives no refund. This opaque-envelope budget is separate from phone semantic admission. A suppressed alert leaves the encrypted request queued, preserves any already queued collapsed alert, and schedules an ordinary silent wake only under the existing active-plan, recipient and silent-budget rules. Unfetched, unexpired access requests remain eligible for pending-wake retries and contact checks. There is no delayed visible alert. Delivery is best effort: on the next open, the app fetches queued requests and presents those admitted by the phone even if no wake arrived. Suppression alone neither rejects the request nor consumes phone semantic admission; neither a push nor relay acceptance proves consent.

Allowed writes add only the approved write types to the app allowance and request Health sharing only for those exact types, without adding reads; agent scope and iOS write permission still apply. If writing was off or the agent's effective write allowance was empty, its write scope becomes only the approved write types, even from `all` or an absent scope; otherwise existing write scope is unioned as before. Decline revokes nothing. The reply alone never updates cached scope; wait for the next ordinary sync. No phone app version or access-request capability is exposed in sync or status. If no matching `access_reply` arrives after an `access_request`, have the owner open Syncky and sync; if it remains missing, check whether consent is still pending on the phone and whether the request expired, then suggest the owner check for an app update without looping. The phone may be offline or consent pending; missing replies establish neither consent nor a decline. Explain expiry from the timestamps rather than inventing a reply. Syncky cannot observe Health read authorization.

Scope release: from agent 0.1.4 with phone app 0.1.4, give up Health types the agent no longer needs with generic `send --type scope_release` (MCP `syncky_send`). The inner is `{"v":1,"type":"scope_release","read":[…],"write":[…]}`: both arrays present, at least one catalog name, writable names on the write side; the agent sorts, deduplicates and always validates it. It only reduces access, so it needs no owner approval and the phone shows no prompt: the phone removes those types from this agent's access at once, stops sending them and rejects writes for them. The owner's own Health selection and iOS permissions do not change, and data the agent already received is not deleted. The phone sends no reply. `status` reports `scope_release` for that phone with `state`: `pending` until a sync that the relay accepted after the release arrives, `applied` when that sync's scope no longer contains the released types, `not_supported` while it still does, and `failed` when the release could not be sent. `not_supported` is provisional: one sync already under way can still carry the old scope, and a later narrowed scope turns it into `applied`. When it persists, either the phone app is older than 0.1.4 and ignores the message, or the phone first fetched the release more than 7 days after it was sent and dropped it; send it again once. To use a released type again, send an ordinary `access_request`.

Unlisted received types accept either authenticated data or control kind without a marker, within the existing 262144-byte data / 4096-byte control envelope limits. Unlisted sends use control without a marker. Selftest covers transport, crypto and pairing vectors.

## Rejected write details

Rejected `sync.acks` and direct-server `results` may include an optional `detail` matching `^[a-z_]{1,32}$`. Older phones omit it. Unknown well-formed details are retained; handle them by `reason`. Ignore a malformed detail or one on a non-rejected status without discarding the ack; the thin transport preserves the raw inner JSON unchanged in the inbox. The phone reports the first failing policy check. These are phone outcomes, never medical advice. Correct encoding, unit and time errors, but never change a measured value, invent a timestamp or clamp a value to pass a check; if the real data cannot be represented, stop and tell the owner.

| Reason | Detail | Meaning | What to fix |
| --- | --- | --- | --- |
| `invalid` | `end_in_future` | `end` is later than the phone's now + 1 hour. | Correct time errors; use `end = now` only when that accurately describes the data. For a running daily total, update the same command by incrementing its version. |
| `invalid` | `span_too_long` | `end − start` exceeds the type's `max_span_s`. | Split the period only where the data genuinely covers separate intervals; otherwise do not write it. |
| `invalid` | `bad_interval` | `start` or `end` is missing/malformed, or `start > end`. | Supply valid RFC 3339 timestamps with `start ≤ end`. |
| `invalid` | `bad_value` | Quantity `value` is missing or is not a finite number. | Send a finite JSON number, not a numeric string or null. |
| `invalid` | `bad_unit` | Quantity `unit` is null, not a string or outside the type's unit family; any unit on a category write also fails here. | Use a string in the type's [unit family](../../protocol/units.json) for quantities; omit `unit` entirely for categories. |
| `invalid` | `bad_category_value` | Category `value` is missing, not a string or outside the type's enum. | Use an exact category value from the catalog. |
| `invalid` | `unknown_op` | `op` is neither `write` nor `delete`. | Use one of those two operations. |
| `type_not_in_scope` | `declined_by_user` | The owner explicitly declined this write type for this agent. | On `declined_by_user`, stop automatic writes and access requests for that type. A later `access_request` requires renewed explicit owner intent and phone availability after its seven-day decline wait and other per-type waits (`next_available_at` when supplied). Retry a write only after the next authenticated sync shows that type in the effective write scope and the owner has approved the write. |
| `invalid` | Absent or unknown | Command validation failed without a recognized sub-reason. | Check operation, value, unit and interval against the catalog. |
| `type_not_in_scope` | Absent or unknown | The type is outside the agent's effective write scope. | Stop sending it until the announced scope includes it. |
| `type_not_allowed` | Absent or unknown | The type is unknown, not writable or not allowed by the phone. | Check catalog `write` support and the owner's Health selection and writing settings, or the agent's pairing grant. |
| `value_out_of_range` | Absent or unknown | The converted quantity is outside catalog bounds or is not finite. | Check the unit and the conversion; if the measured value really is outside the catalog bounds, do not write it, tell the owner. |
| `healthkit_denied` | Absent or unknown | HealthKit refused the operation. | Ask the owner to check iOS Health write permission before retrying. |

After correcting a rejected command, increment its version; resend identical commands with the same id/version only for delivery retries. A detail is explanatory and grants no permission to write.

## Skill trust

Offline skill and literal diff come from package bootstrap or the verified installed bundle. Ed25519 verifies exact payload bytes; pinned HTTPS syncky.app/dev.syncky.app origins, no redirects, bounded fetch, monotonic version and atomic skill/table/schema activation are required. Empty production pin returns skill_key_unset before fetching. A newer package bootstrap supersedes older installed state (`status.skill.state = bootstrap`). Unreadable/corrupt installed state uses that bootstrap with `skill_state_invalid`; corrupt update metadata resets to idle update work and reports the same code. These failures never block status, send, receive or ACK. Each heartbeat carrying a hint resets its bounded retry budget; a different unverified hint can replace a higher version, while verified high-water still rejects downgrades. Hint whats_new and protocol-incompatible notices are advisory, never executable instructions. No binary auto-update controls exist.

If an installed `previous` bundle cannot be verified, it is omitted while the verified active bundle and high-water mark stay intact; `syncky skill --diff` then reports `previous_version: null` and shows the whole current skill as additions.

## Errors

Exit codes: 0 success, 1 usage, 2 relay, 3 invalid_token, 4 local state/selftest. Error output is metadata-only: no JSON bodies, file contents, Health values, tokens or credentials. Retain the code when reporting to the owner. After invalid_token, stop and tell the owner; never automatically register again. Removed commands fail with usage exit 1. Migration helper codes below describe owner-assisted offline migration, never automatic migration by the runtime.

Optional `hint` metadata provides fixed guidance for `forget` (`invalid_transition` on a joined or confirmed phone) and `reject` (a relay failure after local rejection).

CLI errors and MCP tool failures also include fixed per-code `hint` guidance. Unknown codes use a fixed safe fallback; no hint is taken from relay text or an exception message. The guarded forget/reject guidance above takes precedence. Existing error `code`/`error` and safe `detail` remain available. Requested pairing scope and scope-release validation expose safe details (`malformed`, `empty`, `unknown_type`, `not_writable`, `too_large` where applicable); a non-writable pairing request can also name the validated `types`. No pairing or send was admitted on these validation failures.

Send receipts are returned metadata, including through `status.sends` and MCP. Fields are `msg_id`, `kind`, `type`, `to`, `state`, and, when available, `seq`, `attempts`, `next_attempt_at`, `retry_after_until` and `code`. Deadlines use epoch milliseconds (legacy next-attempt timestamps can be ISO strings). Optional `relay_code` is an allowlisted relay or client cause, falling back to `relay_error`; `relay_status` is an HTTP status integer, or 0 for a transport failure or unavailable/invalid status. Optional `hint` is fixed local guidance derived from receipt state and cause, never remote instructions. Later failures replace cause metadata; success clears it and the hint.

`pending` means queue admission, including `rate_limited`/`send_retry`: run the separately authorized receiver to retry after the deadlines and Retry-After; do not enqueue a duplicate. `failed` is terminal, including exhausted retry attempts even if `code` is `send_retry`; this entry will not retry. Resolve the cause with the owner before any new send. `sent` means durable relay acceptance with `seq`, not phone application; correlate phone replies/acknowledgements in inbox. Returned pending, sent and failed receipts preserve CLI exit 0 and MCP `isError: false`. Thrown errors retain the exit mapping above and MCP tool `isError: true`.

Phone access request details: use `syncky send --type access_request --json <file|-> --validate` after explicit owner approval. Select the sole confirmed phone automatically; use `--to <member_id>` when several are confirmed. Access reasons are plain text, at most 200 Unicode code points; there is no item-count cap, but both request and reply must fit 4096 bytes. The compatibility outcome `pending_limit` retains its request-level availability time. Access requests use generic `send --type access_request`; explicit owner approval is separate from permission to write Health values. Read actual `access_reply` item outcomes (`allowed`, `declined`, `needs_health_settings`, `refused`) through inbox, then effective scope from the next ordinary sync. From phone 0.1.3, the phone keeps one pending request per agent binding, with five admitted events per rolling 24 hours, including at most three admitted amendments per pending request. Amendments keep the original expiry, up to 24 hours from creation. The phone timestamps each type when admitted, tracking read and write independently for the 24-hour wait. Only an owner-declined shown type starts a seven-day wait across both read and write. Choices made at pairing have no quota; a type declined at pairing starts the same seven-day wait. Pairing grants create no request timestamps, admissions or amendments. Pairing declines do create the seven-day decline wait across read and write. Filtered items do not reset waits or consume admissions. There is no item-count cap; each request/reply must fit 4096 serialized bytes.

A mixed `resolved` reply combines owner outcomes with `refused` items carrying `reason: requested_recently | declined_recently` and per-item `next_available_at`. Fully filtered requests receive `filtered` immediately without a consent sheet. `rate_limited` has empty sides, request-level `next_available_at` and `limit_reason: daily_ceiling | amendment_limit`; legacy replies may omit the limit reason. Send only the remaining needed types with explicit owner approval. An eligible request while one is pending receives `merged` under its own ref with `merged_into` naming the root; any items in that acknowledgement are refusals, never grants. Await the root's one terminal `resolved` or `expired` reply, whose `merged_refs` correlate all admitted aliases; keep both records even if they arrive out of order. Its canonical union can contain more items than the original request. After an answer, other eligible types can be requested immediately within the ceiling. Never automatically evade a wait by changing the reason or reference, splitting requests or resending filtered types. No local admission/cooldown policy exists.

Health read permission is unobservable. For `needs_health_settings`, follow the phone's conditional instructions at **Health › Sharing › Apps › Syncky**; stored scope is not read authorization. Repeated sends reuse byte-identical ciphertext; update old endpoints before retrying unsupported requests. Approval to request access is separate from permission to write Health values.

AAD appends `|control` before the optional `|diagnostics=<value>` or `|access=<value>` (mutually exclusive). Marked traffic uses an independent relay lane on every plan for diagnostics; access uses ordinary shared relay limits, including HTTP 429 Retry-After. Never strip authenticated markers to bypass a refusal.

The phone's Check the relay connection prepares no upload. A notification tap opens Review for its matching pending request and prepares a preview locally without sending. Only manual Send or Confirm sends a report; decline sends only a small encrypted reply. Arrival alone prepares nothing. APNs acceptance is not delivery. Reports remain private untrusted JSON in the raw 30-day inbox; no local diagnostics retention scheduler or cooldown exists.

Poll metadata uses `poll_interval_s`, `last_poll_at`, `last_ack_at`, `next_poll_at`, `poll_retry_at` and `ack_retry_at`. Receive caches E14 hub state on startup, at most every five minutes, and after hub events; older in-flight responses cannot overwrite newer events. Read-only status never refreshes it. Sending does not bypass the cadence; after first sync completes, use the advertised interval when waiting for new replies. Hub deletion/revocation never clears local history; use a new home only with owner approval.
