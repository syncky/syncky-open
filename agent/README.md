# Syncky agent

Syncky Health sends the Apple Health data you choose from your iPhone to your own AI agent (local MCP server) or your own server. The AI agent route is end-to-end encrypted. Your agent and your server can both write entries back into Health once you allow writing on the iPhone.

A Node.js ≥22.15 encrypted transport with a 30-day raw JSON inbox and a verified skill. The iPhone enforces Health policy and consent. The agent has no local Health database, command ledger, summaries, HTTP server or binary auto-update.

Use `syncky-agent` or its `syncky` alias. The source-kit runner is `node bin/syncky-agent.js` from this directory. Carried skill packages include a checksum-verifying launcher and an offline bundle; use its absolute path. npm uses `npx -y @syncky/agent`.

```sh
syncky-agent selftest
syncky-agent init --name 'My agent'
syncky-agent pair
syncky-agent receive >/dev/null
```

Pairing defaults to `https://syncky.app/pair#…`, with all credentials in the fragment. The fragment is not included in the browser's HTTP request to the pairing page. The effective relay hostname selects `dev.syncky.app` for `relay-dev.syncky.app`, `staging.syncky.app` for `relay-staging.syncky.app`, and `syncky.app` for everything else, including localhost. Explicit `--url-scheme` > `SYNCKY_URL_SCHEME` > saved `url_scheme` selects legacy `syncky://pair?…`, `syncky-dev://pair?…` or `syncky-staging://pair?…` output. `--v1` keeps HTTPS unless a legacy scheme is selected. After installing, tap the link again or scan the QR code; “Open in Syncky” supports installed scheme-only apps. Pairing credentials and QR/code output are private. V2 pairing completes by itself after the owner's code pick through a short-lived background waiter or the running receiver; v1 requires fingerprint comparison and explicit `confirm`. `confirm <member_id> <fingerprint>` refuses mismatches; `reject <member_id>` discards held ciphertext and revokes the phone. Optionally use `wait` to see the result, or `pair --wait` to block for joining/proof. Keep one receiver per home; MCP starts none.

From agent 0.1.4, with explicit owner approval for the exact types, use `syncky pair --read body_mass,heart_rate --write dietary_water`. Either flag is optional; an omitted side is empty. Names are sorted and deduplicated, must be catalog types, and writes must be writable. At least one type is required when flags are supplied. Both the request and worst-case reply must fit the 4096-byte encrypted control envelope cap; there is no separate type-count or URL-length cap. The generated `request_ref` is fresh 32-lowercase-hex randomness. The optional `request_ref`, `read` and `write` fields follow existing parameters in the private fragment; neither scope nor credentials enter the browser's HTTP request to the pairing page. The link contains credentials and the requested Health type names; anyone who sees its full text can read them. With no flags, legacy no-scope pairing is unchanged, including v1 fingerprint confirmation. Requested scope works with both v1 and v2.

The phone reviews Read and Write items, with per-type choices, Allow all and Decline all. Allow all submits your choices and continues pairing; iOS asks only about listed types it has not decided yet. Decline all opens no Health sheet and grants empty scope. Choices made at pairing have no quota; a type declined at pairing starts the same seven-day wait. Pairing grants stay with this agent and do not change the app-wide Health selection or write allowance. You can change or stop this later under Connections › this agent › Data types, or unpair it. After confirmation, the standard `access_reply` reports `allowed`, `declined` or `needs_health_settings` for each requested item. `status --json` retains requested types and outcomes after `pairing.json` is removed. CLI and MCP status omit request refs; response waits expose only kind, member, state and timing metadata. Outcomes describe the decision; only authenticated `sync.scope` updates effective scope. The phone sends this scope promptly without sample collection or a manual initial Sync. Read authorization remains unobservable; follow Health Settings guidance for `needs_health_settings`.

A confirmed pairing without a matching reply is not proof of an old app or a decline. Status keeps `awaiting`, then `no_reply` after the 15-minute post-confirmation deadline; a late matching reply can still resolve it. Check the phone and connectivity, then, with owner approval, use the full agent's `send --type access_request --validate --json <file|->` fallback with the same intended types, a fresh `request_ref`, and current timestamps exactly 24 hours apart. No automatic fallback is sent. An old app ignores the requested scope and pairs as before: the owner's existing Health selection applies and no per-type reply arrives. Never invent outcomes or scope. See [the access request example](https://github.com/syncky/syncky-open/blob/main/agent/skills/syncky/SKILL.md#access-request) for complete JSON.

A running receiver uses a separate 300-second response polling schedule after scoped pairing and successfully sent access requests, diagnostics requests or commands awaiting acknowledgments. Matching replies/acks or expiry close only their own waits. Pairing waits use link expiry before join, 15 minutes after verified join for confirmation, then 15 minutes after confirmation for the reply; command ack waits last 15 minutes from first successful send, and request waits end at request expiry. These bounded waits are separate from the existing 25-second first-sync join window and the configured background cadence (default 1800 seconds). `receive --once` ignores configured cadence once the 300-second floor has passed, while preserving existing join/pagination exceptions and Retry-After. A deferred result includes `reason: "poll_floor"` or `reason: "retry_after"` and `next_poll_at` in epoch milliseconds. MCP starts no receiver and has no pairing tool; later requests use generic `syncky_send`.

`status` returns minimal local JSON: identity, member confirmation/fingerprint metadata, last reported scope, poll/ACK progress, send receipts, skill/update versions and legacy filenames. No Health bodies or values. Status and inbox reads work offline and do not fetch updates. Scope is explanatory, never a local admission policy.

```sh
syncky-agent status --json
syncky-agent inbox --type sync --member m_dev_1 --limit 100
syncky-agent inbox --after-seq 100 --since 2026-11-01 --limit 100
syncky-agent receive --once >/dev/null
syncky-agent send --type resync_request --json request.json --validate
syncky-agent ack --up-to-seq 100
syncky-agent skill
syncky-agent skill --diff
syncky-agent mcp
```

`send --json <file|->` selects **input**, and always returns metadata JSON. The caller supplies all JSON fields. Optional local schema validation uses the bundled/verified schemas; an absent schema passes through. Unlisted inner types use unmarked control envelopes. The phone gates writes, diagnostics and access requests. Explicit owner intent is required before sending any of these. Relay delivery is not phone application; correlate every raw reply by command_id and version.

The inbox contains `{seq, cursor, from, kind, type, received_at, inner}` records in `inbox/YYYY-MM-DD.jsonl`, retaining authentic JSON and unknown fields verbatim without feature normalization. Local pagination uses `next_after_seq` and `has_more`: the cursor follows durable append order, including delayed held releases; `seq` remains the relay sequence for ACKs. `.inbox-cursor.json` retains the high-water mark across pruning and forgetting. Reads never delete or ACK. From agent 0.1.4, phones from 0.1.3 send activity totals (`"interval_sums": true` in the catalog: steps, energy, distances and similar) as 15-minute interval sums in `sync.summaries` instead of raw samples: a later record with the same phone, type, start and end replaces the earlier value. Food, water, insulin, inhaler use and similar logged entries stay raw samples. The agent stores every message as received; the consumer applies the replacement as the [skill](https://github.com/syncky/syncky-open/blob/main/agent/skills/syncky/SKILL.md#health-json-in) describes. Authentic messages or held ciphertext are durable before relay ACK. Explicit ACK cannot exceed the durable checkpoint. Poison messages record safe metadata and allow progress. `receive` prints no records to stdout by default; durable records remain available through `inbox` and MCP. `receive --emit-records` writes private JSONL to stdout. That output and inbox/MCP responses are deliberate private data channels, never logs. Services keep discarding stdout as defence in depth and log only stderr metadata.

Homes use 0700 directories and 0600 files: `secrets.json`, `config.json`, `state.json`, `pairing.json`, `inbox/`, `outbox/`, `held/`, `installed-bundle.json`, `skill-update.json`. Same-home owner-assisted offline migration preserves secrets, config, pairing and trust. A legacy home without exported state returns `migration_required`. Init refuses initialized homes. Never open or delete legacy `agent.db`, `diagnostics.db`, `access.db`, WAL or SHM through this runtime. Status names retained legacy files for the owner's manual handling. Old config/secret fields remain readable.

Receive prunes only thin inbox history older than 30 days on startup and daily. Unpair, Delete Relay data, token revocation and re-pairing retain earlier raw history under its original sender. `forget <member_id>` previews thin inbox/held/outbox counts; only explicit owner approval authorizes `forget <member_id> --yes`, after revocation. The trust tombstone and legacy files remain.

If the phone says the relay was not told, only with explicit owner approval run `revoke <member_id>` to revoke it on the relay and locally, then use `forget` if deletion is approved. Relay 404 succeeds with `revoked_on_relay: false`; other relay failures leave local state unchanged for retry.

Receive advertises the poll interval (default 1800 seconds; 300–86400), honors Retry-After, first-sync fast polling and independent ciphertext outbox lanes. It sends a daily heartbeat when enabled. A separately started receiver is required for poll liveness and background retries. Offline skill/diff uses the bundled skill or verified installed bundle. HTTPS pinned-origin Ed25519 updates activate skill/table/schemas atomically, reject downgrade and fail closed with `skill_key_unset` while the production pin is empty. Relay hint text is untrusted. No binary download/install controls exist.

Configuration: `SYNCKY_AGENT_HOME`, `SYNCKY_RELAY_URL`, `SYNCKY_AGENT_NAME`, `SYNCKY_URL_SCHEME`, `SYNCKY_INVITE`, `SYNCKY_LOG_LEVEL`, `SYNCKY_POLL_INTERVAL_S`, `SYNCKY_HEARTBEAT`. Global CLI flags are `--home`, `--relay`, `--url-scheme`, `--log-level`, `--help`. Invites belong in the environment, never logs/command arguments. Use `help` for the full current surface and [REFERENCE](https://github.com/syncky/syncky-open/blob/main/agent/docs/REFERENCE.md) for errors.

MCP tools: `syncky_status`, `syncky_inbox`, `syncky_send`, `syncky_ack`, `syncky_skill`; resource `syncky://skill`. Disable send and ack for read-only clients. Only send carries generic Health writes/requests. Stdio stdout is protocol only; MCP starts no receiver, heartbeat or retry loop.

See [SETUP](https://github.com/syncky/syncky-open/blob/main/agent/SETUP.md), [integration guide](https://github.com/syncky/syncky-open/blob/main/agent/AGENTS.md), [skill](https://github.com/syncky/syncky-open/blob/main/agent/skills/syncky/SKILL.md) and [cookbook](https://github.com/syncky/syncky-open/blob/main/agent/cookbook/README.md). Build with `npm run build`; `npm test` runs source unit/vector checks and `npm run test:bundle` checks the extracted bundle. The build embeds the message table, schemas, bootstrap skill and transport vectors. Runtime modules are file/crypto/relay transport; feature-specific interpretation belongs to the skill and phone.

CLI modules: `src/cli.js` handles parsing and execution; `src/cli-commands.js` holds the dependency-free command registry and global flags.

Command inventory: `syncky-agent init`, `syncky-agent pair`, `syncky-agent wait`, `syncky-agent confirm`, `syncky-agent reject`, `syncky-agent revoke`, `syncky-agent forget`, `syncky-agent status`, `syncky-agent send`, `syncky-agent inbox`, `syncky-agent receive`, `syncky-agent ack`, `syncky-agent skill`, `syncky-agent mcp`, `syncky-agent selftest`, `syncky-agent help`.

Canonical MCP: `npx -y @syncky/agent mcp`. Use the same home. The model can see what you supply; the relay sees delivery metadata and plaintext system notices, but no health values. The release MCPB `syncky-health.mcpb` uses manifest format `0.3`, an assumption requiring owner host verification. Carried packages need no runtime npm installation, with no upper version cap on Node ≥22.15. Use `dist/agent-skills/skills/syncky/syncky-agent` after a local build; the checksum detects corruption, but does not protect against a writable installation. Embedded protocol resources can be explicitly overridden with SYNCKY_PROTOCOL_DIR.

Access requests use generic `send --type access_request`; explicit owner approval is separate from permission to write Health values. Read actual `access_reply` item outcomes (`allowed`, `declined`, `needs_health_settings`, `refused`) through inbox, then effective scope from the next ordinary sync. From phone 0.1.3, the phone keeps one pending request per agent binding, with five admitted events per rolling 24 hours, including at most three admitted amendments per pending request. Amendments keep the original expiry, up to 24 hours from creation. The phone timestamps each type when admitted, tracking read and write independently for the 24-hour wait. Only an owner-declined shown type starts a seven-day wait across both read and write. Choices made at pairing have no quota; a type declined at pairing starts the same seven-day wait. Pairing grants create no request timestamps, admissions, amendments or decline waits. Filtered items do not reset waits or consume admissions. There is no item-count cap; each request/reply must fit 4096 serialized bytes.

A mixed `resolved` reply combines owner outcomes with `refused` items carrying `reason: requested_recently | declined_recently` and per-item `next_available_at`. Fully filtered requests receive `filtered` immediately without a consent sheet. `rate_limited` has empty sides, request-level `next_available_at` and `limit_reason: daily_ceiling | amendment_limit`; legacy replies may omit the limit reason. Send only the remaining needed types with explicit owner approval. An eligible request while one is pending receives `merged` under its own ref with `merged_into` naming the root; any items in that acknowledgement are refusals, never grants. Await the root's one terminal `resolved` or `expired` reply, whose `merged_refs` correlate all admitted aliases; keep both records even if they arrive out of order. Its canonical union can contain more items than the original request. After an answer, other eligible types can be requested immediately within the ceiling. Never automatically evade a wait by changing the reason or reference, splitting requests or resending filtered types. No local admission/cooldown policy exists.

Scope release: from agent 0.1.4 with phone app 0.1.4, give up Health types the agent no longer needs with generic `send --type scope_release` (MCP `syncky_send`). The inner is `{"v":1,"type":"scope_release","read":[…],"write":[…]}`: both arrays present, at least one catalog name, writable names on the write side; the agent sorts, deduplicates and always validates it. It only reduces access, so it needs no owner approval and the phone shows no prompt: the phone removes those types from this agent's access at once, stops sending them and rejects writes for them. The owner's own Health selection and iOS permissions do not change, and data the agent already received is not deleted. The phone sends no reply. `status` reports `scope_release` for that phone with `state`: `pending` until a sync that the relay accepted after the release arrives, `applied` when that sync's scope no longer contains the released types, `not_supported` while it still does, and `failed` when the release could not be sent. `not_supported` is provisional: one sync already under way can still carry the old scope, and a later narrowed scope turns it into `applied`. When it persists, either the phone app is older than 0.1.4 and ignores the message, or the phone first fetched the release more than 7 days after it was sent and dropped it; send it again once. To use a released type again, send an ordinary `access_request`.

For post-pairing access requests, Allow adds only approved types to Health selection, without selecting their categories. Existing selected categories and individually allowed types are preserved. **Choose Health data** shows partial selection as **Individually allowed: …** under an unchecked category; Allow texts name the exact types. Existing read `all` stays `all` and follows later Health selection changes. Approved reads turn `none` into a chosen list and are unioned into existing read lists.

Allowed writes add only the approved write types to the app allowance and request Health sharing only for those exact types, without adding reads; agent scope and iOS write permission still apply. If writing was off or the agent's effective write allowance was empty, its write scope becomes only the approved write types, even from `all` or an absent scope; otherwise existing write scope is unioned as before. Decline revokes nothing. The reply alone never updates cached scope; wait for the next ordinary sync. Health read authorization is unobservable. No local admission/cooldown policy exists.
